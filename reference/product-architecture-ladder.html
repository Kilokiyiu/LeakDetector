产品架构梯子

这份速查回答三个问题：它讲什么、何时打开、读完能做什么。 它讲的是从「读懂一个方法」爬到「能拆一个新产品」的固定梯子。 当你已经能跟上对象传递，却不知道怎样把方法里的设计迁移到新产品时打开它。 读完后，你应当能提出五道决策题，并能用五步画出阶段与契约草图。 配套短课是 0010。 本文只写架构与现行决策；实现细节打开对应源码。

三层问题分别通向什么结果？

学习时若把运行、决策、产品混成一锅，你会在错误的层级消耗注意力。 下表把三层拆开：每一层只问一类问题，并对应一种可检查的输出。

层核心问题你应得到的输出
运行 这段代码怎样执行？ 能带着一条真数据在源码里跟完
决策 为什么这样切，而不是那样切？ 能说出边界、契约与失败策略及原因
产品 换一个产品时阶段怎样画？ 有阶段图，并能做最薄竖切验证

课 0009 主要帮你站稳运行层；本页与课 0010 把重心放在决策层与产品层。

读一个方法时该问哪五道决策题？

「决策题」指的是关于边界与契约的问题，而不是关于某一个 API 重载签名的问题。 你对翻译步骤（或任意核心方法）提问时，固定使用下面五题，以便答案可迁移。

  1. 边界：它绝不做什么？为什么必须绝不做？
  2. 契约：它依赖哪些字段或类型名？这些名字为什么重要？
  3. 形状：为什么选用这种数据结构，而不是更「随便」的表示？
  4. 失败：坏输入时选择抛错、跳过还是降级？这样选是为了避免什么风险？
  5. 替换：换格式或换平台时，什么必须留下，什么可以整段替换？

五题都要求同时写出「做了什么」和「为什么」，这样你带走的是设计理由，而不是一次性的实现记忆。

拆一个新产品时走哪五步？

当你面对一个新的「采集 → 结论 → 展示」类需求时，先用五步锁骨架，再写代码。 这样做是为了先保护重要决策，避免一上来就被某个平台 API 牵着走。

  1. 用一句话写清工作：谁、在什么情境、要得到什么结果。
  2. 切阶段：采集、翻译、判断、展示（名称可改，阶段不要揉在一起）。
  3. 为每阶段写下「必须做」与「绝不做」。
  4. 写清阶段之间的交接契约（文件格式、事件模型或报告对象）。
  5. 用一条真数据做最薄竖切跑通，再考虑测试与加固。

五步的终点是「可运行的细竖条」，而不是一份无法验证的宏大设计图。

本仓库的阶段怎样对照？

下表把梯子落到 LeakDetector 的现行模块上。 你可以用它检查自己画的阶段图是否与仓库边界一致。

阶段落点绝不做（及原因）
采集 include/ 不做复杂报告排版，以免与被测程序强耦合展示逻辑
契约 JSONL 文件 —
翻译 Parsers 不判泄漏，以免解析格式变更时误伤判定
判断 Core 不读文件、不打控制台，以便同一算法服务多种入口
展示 Reporters 不再算一遍泄漏，以免出现两套互相打架的结论
门面 CLI 不塞业务算法，以免门面变胖、难以测试

若某一步「绝不做」被打破，通常意味着边界已经开始腐烂，后续改动成本会上升。

学习时怎样对待文档？

阅读与笔记时遵守下列现行约定，这样你的笔记不会和仓库文档规则打架。

  • 把架构文档当作地图，实现细节打开对应源码。
  • 只记录现行决策；不保留作废史，也不把临时 phase 施工表写进正式材料。
  • 从 docs/README.md 进入导航，再按读者目标选择下一篇。

这些约定让文档保持可扫描，并让 git 去承担变更历史。

翻译步骤的决策摘要是什么？

下面用四行概括 Parsers 翻译一步的现行决策。 它帮助你默写「输入 / 输出 / 失败 / 绝不」，具体 API 仍以 JsonlEventParser 为准。 

输入：一行 JSON 字符串
输出：分配、释放或摘要事件之一
失败：缺少或未知 event 时抛错
绝不：更新 live 集合，也不写报告

若你能合上材料复述这四行并说出每一行的原因，决策层就算过关。
