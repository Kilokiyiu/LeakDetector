## 1. `leak_detector.h` 的作用

### 1.1 它是什么

`leak_detector.h` 是本项目的 **C++ 注入头文件**：用户在自己的 C++ 程序里 `#include` 它之后，程序中所有通过 `new` / `new[]` 分配的堆内存都会被自动登记；对应的 `delete` / `delete[]` 会把登记移除。程序结束前调用 `ReportLeaks()`，即可在控制台看到**还有哪些块没有被释放**——也就是内存泄漏，以及泄漏发生在哪个源文件的哪一行。

它是 LeakDetector 工具链在 **v0.1 阶段唯一需要用户接入的组件**，不依赖 Valgrind、不依赖 C# 运行时，单独就能完成「检测 + 报告」。

### 1.2 它解决什么问题

C++ 堆内存不会自动回收。程序员写了 `new` 却忘记 `delete`，或者异常导致 `delete` 没执行，堆上的对象就会一直占着内存。程序退出后，操作系统会收走进程的全部内存，所以**小泄漏往往「看不出来」**；但在长期运行的服务、游戏、嵌入式场景里，泄漏会累积直到 OOM。

`leak_detector.h` 的作用就是在**开发/调试阶段**帮你回答：

> 「这次运行里，有哪些 `new` 出来的内存，到程序结束还没被 `delete`？」

并尽量告诉你：**哪一行 `new` 的**（通过 `__FILE__` / `__LINE__`）。

### 1.3 它在整个项目中的位置

LeakDetector 的长期架构是「C++ 侧记录 + C# 侧分析」。`leak_detector.h` 负责**前半段**——在目标程序内部拦截分配/释放：

```
┌─────────────────────────────────────────────────────────┐
│  用户的 C++ 程序                                         │
│    #include "leak_detector.h"                           │
│    new / delete 被宏 + operator 重载拦截                  │
└──────────────────────────┬──────────────────────────────┘
                           │
           v0.1             │  g_allocMap + ReportLeaks()
                           │  → 直接打印到控制台
                           │
           v0.2（计划）      │  每次 alloc/free 追加写 JSONL 日志
                           ↓
┌─────────────────────────────────────────────────────────┐
│  C# 分析器（LeakDetector.CLI / Analyzers / Reporters）  │
│    读取日志 → 配对分析 → 格式化报告（JSON / HTML）       │
└─────────────────────────────────────────────────────────┘
```

| 版本 | `leak_detector.h` 的职责 |
|------|-------------------------|
| **v0.1** | 内存里维护分配表，程序内调用 `ReportLeaks()` 输出 |
| **v0.2** | 同上，并额外把事件写入 JSONL，供 C# 解析 |
| **v0.3+** | CLI 可能包装「编译 + 运行 + 分析」一整条命令 |

没有这份头文件，C# 模块就没有数据来源——它无法凭空知道你的程序里发生了哪些 `new`。

### 1.4 工作原理（一句话）

**每次分配建账，每次释放销账，结束时看还没销账的。**

这与 Valgrind Memcheck 里 `MC_Chunk` 哈希表 + 程序退出 leak summary 的思路一致，只是实现方式不同：

| | Valgrind Memcheck | `leak_detector.h` v0.1 |
|--|-------------------|------------------------|
| 如何拦截 `new` | 二进制插桩，替换 malloc/free | 宏 `#define new` + 重载 `operator new` |
| 分配记录 | `MC_Chunk` 挂哈希表 | `AllocRecord` 挂 `unordered_map` |
| 泄漏判定 | 遍历哈希表 + 指针可达性分析 | map 中剩余条目即泄漏 |
| 定位 | 调用栈 | 源文件 + 行号 |
| 越界 / 未初始化 / use-after-free | 影子内存检测 | **不检测** |

详见 [mc_include.md](../mc_include.md) 中 MC_Chunk 的说明；`leak_detector.h` 是其在学习阶段的**最小可用子集**。

### 1.5 它能检测什么 / 不能检测什么

**v0.1 能检测：**

- `new` / `new[]` 之后从未 `delete` / `delete[]`（definite leak 的简化版）
- 泄漏块的大小和大致分配位置（file:line）

**v0.1 不能检测：**

- `malloc` / `free`（未拦截 C 库分配）
- 缓冲区溢出、读写已释放内存（无影子内存、无 RedZone）
- 使用未初始化的堆内存
- `new[]` 配 `delete`（非 `delete[]`）的语义错误（v0.4 计划）
- Valgrind 的 Indirectly Lost / Possibly Lost / Still Reachable 等精细分类
- 第三方库内部的 `new`（若该库在 include 头文件之前已完成分配）

### 1.6 用户怎么用

开发者在**自己的** C++ 工程里：

1. 把 `LeakDetector/include/leak_detector.h` 加入 include 路径
2. 在**所有其他 `#include` 之后**加入 `#include "leak_detector.h"`
3. 正常写 `new` / `delete`（宏会自动替换）
4. 在 `main` 返回前（或测试结束处）调用 `ReportLeaks()`

不需要改链接选项、不需要像 Valgrind 那样用 `valgrind ./program` 包一层运行。代价是：**必须重新编译**，且宏替换对代码有一定侵入性。

### 1.7 为什么用头文件 + 宏，而不是 Valgrind 那种方式

| 方式 | 优点 | 缺点 |
|------|------|------|
| **头文件 + 宏（本项目 v0.1）** | 实现简单、便于学习、Windows 上可直接用 | 需改源码、宏有陷阱、覆盖范围有限 |
| **Valgrind 二进制插桩** | 不改源码、检测全面 | 仅 Linux 为主、实现极复杂、慢 |
| **MSVC `_CRTDBG_MAP_ALLOC`** | Windows 内置 | 主要面向 CRT malloc，对 `new` 支持有限 |

学习阶段先用头文件跑通「分配追踪 → 泄漏报告」闭环；理解 MC_Chunk 和泄漏检测逻辑后，再考虑向日志 + C# 分析器或更接近 Valgrind 的能力演进。

## 3. 设计目标与范围

### 3.1 v0.1 必须实现

- 用**宏**将用户代码中的 `new` 替换为带 `__FILE__`、`__LINE__` 的 placement 形式
- 重载全局 `operator new` / `operator new[]` / `operator delete` / `operator delete[]`
- 维护「地址 → 分配记录」的全局表
- 提供 `ReportLeaks()`，在程序中手动调用，向 **stdout** 输出泄漏报告
- 对 `delete nullptr` 安全（不崩溃、不报错）

### 3.2 v0.1 暂不实现（留 v0.2+）

- JSONL 日志、C# 分析器对接
- `new(std::nothrow)` 重载
- placement new（`new(p) T`）
- 调用栈捕获
- `MC_AllocKind` 式 `new[]` / `delete` 不匹配检测
- double-free / unknown-free 警告
- `malloc` / `free` 拦截
- 多线程压力测试（mutex 可先写上，不必专门测）

## 4. 核心原理

```
用户写:  int* p = new int(42);
宏展开:  int* p = new(__FILE__, __LINE__) int(42);
              ↓
operator new(size, file, line) 被调用
              ↓
malloc 分配 → 写入 g_allocMap[ptr] = { size, file, line, isArray }
              ↓
用户写:  delete p;   （若未写则 ptr 一直留在 map 中）
              ↓
operator delete(ptr) → 从 map 移除 → free(ptr)
              ↓
ReportLeaks() → 遍历 map 中剩余条目 → 输出泄漏报告
```

对标 Valgrind：相当于简化版 `MC_Chunk` 哈希表 + 程序退出前 leak summary，不做指针可达性扫描。

---

## 5. 数据结构

### 5.1 `AllocRecord`

每条分配记录需保存：

| 字段 | 类型 | 说明 |
|------|------|------|
| `size` | `size_t` | 请求分配的字节数（`operator new` 的 `size` 参数） |
| `file` | `const char*` | 分配发生处的源文件路径（`__FILE__`，字符串字面量，不需拷贝） |
| `line` | `int` | 分配发生处的行号（`__LINE__`） |
| `isArray` | `bool` | `true` = `new[]` 分配；`false` = 普通 `new` 分配 |

> v0.1 中 `isArray` 只用于报告展示（可选后缀 `[array]`），不做 mismatch 检测。

### 5.2 全局分配表

| 项 | 建议类型 | 说明 |
|----|---------|------|
| 容器 | `std::unordered_map<void*, AllocRecord>` | key 为 `malloc` 返回的用户可见指针 |
| 命名 | `g_allocMap`（或放入匿名 namespace / 类内 static） | 全局唯一 |
| 并发 | `std::mutex g_mutex` | 所有读写 map 的操作加锁 |

**不变量**：

- 每次成功的 `new` / `new[]` 在 map 中**恰好**增加一条
- 每次非 null 的 `delete` / `delete[]` 在 map 中**恰好**移除一条（若存在）
- `ReportLeaks()` 时 map 中剩余条目 = 泄漏

## 6. 必须实现的符号

### 6.1 分配：`operator new`

```cpp
void* operator new(std::size_t size, const char* file, int line);
void* operator new[](std::size_t size, const char* file, int line);
```

**行为**：

1. 调用 `std::malloc(size)` 获取内存
2. 若 `ptr != nullptr`：加锁，写入 `g_allocMap[ptr] = { size, file, line, isArray=false/true }`
3. 返回 `ptr`（允许返回 `nullptr` 当 `size==0` 或 OOM 时，与实现相关；v0.1 直接透传 `malloc` 结果即可）

**注意**：这两个是**带 placement 参数的全局 new**，不是 placement new；宏 `#define new new(__FILE__, __LINE__)` 会选中它们。

### 6.2 释放：`operator delete`

```cpp
void operator delete(void* ptr) noexcept;
void operator delete[](void* ptr) noexcept;
```

**行为**：

1. 若 `ptr == nullptr`：直接返回（C++ 标准允许）
2. 加锁，从 `g_allocMap` 中 `erase(ptr)`（不存在则静默忽略，v0.1 不报警）
3. 调用 `std::free(ptr)`

**MSVC 还必须实现 sized delete**（Debug 模式下 `delete p` 会调用它们，否则会走 CRT 的 delete → 对 `malloc` 内存 `abort()`）：

```cpp
void operator delete(void* ptr, std::size_t) noexcept;
void operator delete[](void* ptr, std::size_t) noexcept;
```

实现可与 unsized 版本相同（内部都 `free` + 从 map 移除）。

> 为何用 `malloc`/`free` 而非 `::operator new(size_t)`：避免递归进入自己的分配逻辑。v0.1 简单实现推荐 **malloc/free 配对**。

### 6.3 报告：`ReportLeaks`

```cpp
void ReportLeaks();
```

**行为**：

1. 加锁，读取 `g_allocMap` 快照或直接在锁内遍历
2. 按 §8 格式输出到 `std::cout`
3. 不修改 map（不自动 clear；泄漏条目保留，便于调试）

### 6.4 宏

```cpp
#define new new(__FILE__, __LINE__)
```

**必须放在头文件末尾**（所有 operator 声明/定义之后），且由 `#ifndef LEAK_DETECTOR_H` 保护。

### 6.5 可选：RAII 自动报告

v0.1 **可选**实现，便于用户忘记手动调用：

```cpp
struct LeakDetectorGuard {
    ~LeakDetectorGuard() { ReportLeaks(); }
};
```

若实现，文档中说明：在 `main` 开头定义 `LeakDetectorGuard guard;` 即可。  
`01_simple_leak` 示例**不要求**使用 Guard，要求**显式**调用 `ReportLeaks()`。

## 7. 头文件包含顺序（重要）

用户代码应遵循：

```cpp
#include <iostream>   // 其他标准库 / 第三方库
// ... 其他 #include ...

#include "leak_detector.h"   // 必须放在最后
```

**原因**：`#define new` 会替换后续翻译单元中所有 `new` 关键字。若在其他头文件之前 include，可能破坏 STL 等库内部实现。

**禁用区域**（v0.1 可选提供）：

```cpp
#ifdef LEAK_DETECTOR_DISABLE
  #undef new
#endif
// ... 使用 placement new 或不想被追踪的代码 ...
#ifdef LEAK_DETECTOR_DISABLE
  #define new new(__FILE__, __LINE__)
#endif
```

v0.1 可不实现 `LEAK_DETECTOR_DISABLE`，但在注释中说明限制即可。

## 8. 输出格式规范

`ReportLeaks()` 输出必须严格遵循以下格式，便于与 `expected_output.txt` 做 diff。

### 8.1 无泄漏

```
[LeakDetector] No leaks detected.
```

- 末尾有换行 `\n`
- `detected` 后有一个 `.`

### 8.2 有泄漏

```
[LeakDetector] FOUND <N> LEAK(S):
  LEAK: <size> bytes at <ptr>  [<file>:<line>]
  ...
```

| 占位符 | 规则 |
|--------|------|
| `<N>` | 泄漏块数量，十进制整数 |
| `<size>` | 该块 `AllocRecord.size`，十进制 |
| `<ptr>` | 指针打印格式：`std::cout` 默认，`0x` 前缀十六进制（MSVC/GCC 均支持 `%p` 或 `(void*)ptr`） |
| `<file>` | `AllocRecord.file` 原样输出（通常是 `main.cpp` 或完整路径，取决于编译器） |
| `<line>` | 十进制行号 |

**每条泄漏行前有两个空格缩进**（`  LEAK:`）。

**示例**（指针值每次运行不同，验证时只比对结构和 file:line）：

```
[LeakDetector] FOUND 1 LEAK(S):
  LEAK: 4 bytes at 0x000001a2b3c4d5e0  [main.cpp:12]
```

可选：若 `isArray == true`，行末加 ` [array]`：

```
  LEAK: 40 bytes at 0x...  [main.cpp:15] [array]
```

`01_simple_leak` 不涉及 `new[]`，可暂不输出 `[array]`。

## 14. 代码编写指南（分步实现）

按下面顺序把代码写进 `LeakDetector/include/leak_detector.h`。每一步都可以保存后编译一次，确认没有语法错误。

### 14.1 文件骨架与 include

```cpp
#ifndef LEAK_DETECTOR_H
#define LEAK_DETECTOR_H

#include <cstdlib>      // malloc, free
#include <iostream>     // ReportLeaks 输出
#include <mutex>        // 多线程安全（v0.1 建议写上）
#include <unordered_map>

// ... 中间写结构体、operator、ReportLeaks ...

#define new new(__FILE__, __LINE__)   // 必须放在最后

#endif
```

**要点**：

- `#ifndef` / `#define` / `#endif` 防止头文件被重复包含
- `#define new` **必须放在 `#endif` 之前、且在所有函数定义之后**
- 不要 `#include` 其他可能内部使用 `new` 的第三方头（本头文件自己就是「最后一个 include」）

---

### 14.2 定义 `AllocRecord` 和全局表

```cpp
struct AllocRecord {
    size_t      size;     // operator new 的 size 参数
    const char* file;     // __FILE__，字符串字面量，生命周期贯穿整个程序
    int         line;     // __LINE__
    bool        isArray;  // new[] 为 true，普通 new 为 false
};

inline std::unordered_map<void*, AllocRecord> g_allocMap;
inline std::mutex g_mutex;
```

**要点**：

- `file` 存 `const char*`，**不要** `new` 一份拷贝；`__FILE__` 是编译期字符串常量
- `inline` 写在头文件里，避免多个 `.cpp` include 时出现「重复定义」链接错误
- key 是 `void*`（`malloc` 返回的地址），value 是分配记录

---

### 14.3 写 `operator new`（普通 new）

```cpp
inline void* operator new(std::size_t size, const char* file, int line) {
    void* ptr = std::malloc(size);
    if (ptr) {
        std::lock_guard<std::mutex> lock(g_mutex);
        g_allocMap[ptr] = {size, file, line, false};
    }
    return ptr;
}
```

**逐行理解**：

| 代码 | 作用 |
|------|------|
| `operator new(size, file, line)` | 带额外参数的 new；宏展开后会调用这个版本 |
| `std::malloc(size)` | 真正分配内存；**不要用** `::operator new(size)`，会递归 |
| `if (ptr)` | 分配成功才记账；失败则返回 `nullptr` |
| `lock_guard` | 加锁，防止多线程同时改 map |
| `isArray = false` | 标记这是 `new`，不是 `new[]` |

**宏如何选中它**：

```cpp
int* p = new int(42);
// 预处理器展开为：
int* p = new(__FILE__, __LINE__) int(42);
//                          ↑ 调用上面的 operator new
```

---

### 14.4 写 `operator new[]`（数组 new）

```cpp
inline void* operator new[](std::size_t size, const char* file, int line) {
    void* ptr = std::malloc(size);
    if (ptr) {
        std::lock_guard<std::mutex> lock(g_mutex);
        g_allocMap[ptr] = {size, file, line, true};  // isArray = true
    }
    return ptr;
}
```

与 `operator new` 几乎相同，区别只有：

- 函数名是 `operator new[]`
- `isArray` 设为 `true`

---

### 14.5 写 `operator delete` 和 `operator delete[]`

```cpp
inline void operator delete(void* ptr) noexcept {
    if (!ptr) {
        return;
    }
    {
        std::lock_guard<std::mutex> lock(g_mutex);
        g_allocMap.erase(ptr);
    }
    std::free(ptr);
}

inline void operator delete[](void* ptr) noexcept {
    if (!ptr) {
        return;
    }
    {
        std::lock_guard<std::mutex> lock(g_mutex);
        g_allocMap.erase(ptr);
    }
    std::free(ptr);
}
```

**要点**：

| 代码 | 作用 |
|------|------|
| `if (!ptr) return` | `delete nullptr` 合法，直接返回 |
| `g_allocMap.erase(ptr)` | 从表里销账；key 不存在也不报错 |
| `std::free(ptr)` | 与 `malloc` 配对释放 |
| `noexcept` | 标准库 `delete` 声明为不抛异常 |
| 花括号 `{ lock... }` | 限制锁的作用域，避免持锁调用 `free`（好习惯） |

`delete` 和 `delete[]` 在 v0.1 里逻辑相同，都要写——编译器会根据用户写的是 `delete p` 还是 `delete[] p` 选择对应版本。

---

### 14.6 写 `ReportLeaks()`

```cpp
inline void ReportLeaks() {
    std::lock_guard<std::mutex> lock(g_mutex);
    if (g_allocMap.empty()) {
        std::cout << "[LeakDetector] No leaks detected.\n";
        return;
    }
    std::cout << "[LeakDetector] FOUND " << g_allocMap.size() << " LEAK(S):\n";
    for (const auto& entry : g_allocMap) {
        const void* ptr = entry.first;
        const AllocRecord& rec = entry.second;
        std::cout << "  LEAK: " << rec.size << " bytes at " << ptr
                  << "  [" << rec.file << ":" << rec.line << "]";
        if (rec.isArray) {
            std::cout << " [array]";
        }
        std::cout << '\n';
    }
}
```

**输出格式对照**（必须严格一致，见 §8）：

```
[LeakDetector] No leaks detected.
```
或
```
[LeakDetector] FOUND 2 LEAK(S):
  LEAK: 4 bytes at 0x1234560  [main.cpp:10]
  LEAK: 40 bytes at 0x789abcd0  [main.cpp:11] [array]
```

**注意**：`  LEAK:` 前面有**两个空格**；`FOUND` 和 `LEAK(S)` 之间有空格。

### 14.7 最后加上宏

```cpp
#define new new(__FILE__, __LINE__)
```

放在 `#endif` 前最后一行。之后用户代码里所有 `new` 都会自动带上文件和行号。

| 报错 | 原因 | 解决 |

## 10. 常见陷阱与处理

| 问题 | 现象 | v0.1 处理 |
|------|------|----------|
| 头文件顺序错误 | 编译 STL 报 bizarre errors | 文档强调 include 顺序 |
| 只重载 placement new，未重载 `delete` | 泄漏永远删不掉 | 必须同时实现 delete |
| `delete` 未加 `noexcept` | 部分编译器警告 | 加上 `noexcept` |
| 用 `::operator new(size)` 内部分配 | 无限递归 | 内部用 `malloc` |
| `file` 指针被拷贝到堆后失效 | 乱码 | `file` 只存 `__FILE__` 字面量，不拷贝 |
| 重复 `delete` | 未定义行为（真实程序） | v0.1 不检测；第二次 erase 无操作 + double free（**不要专门测**） |
| MSVC Debug 下 `delete` 崩溃 | 编译器调用 `operator delete(void*, size_t)`，未实现则走 CRT | 必须同时实现 sized delete（见 §6.2） |

## 11. 自测清单
